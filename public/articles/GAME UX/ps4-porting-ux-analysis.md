> 跨平台移植的交互设计核心，在于将PC端“光标+精准点击”的交互模式，平滑迁移至主机端“焦点+方向键”的操作逻辑上。

---

## 核心命题

主机游戏的“简洁”不等于“简单”，而是在**有限操作能力下**实现**高效的交互效率**。

PC端玩家面对的是一个高精度、高自由度的光标，可以任意点击屏幕上的任何一点。而主机玩家手中的手柄，本质上是一套方向输入设备，它通过移动“焦点”来遍历界面上的可交互元素。跨平台移植的UX工作，本质上就是完成从“光标思维”到“焦点思维”的转换。

---

## 一、双端适配策略框架

### 1.1 核心挑战

| 维度 | PC端 | 主机端 |
|------|------|--------|
| 操作方式 | 鼠标+键盘（精准点击） | 手柄（方向输入） |
| 焦点形式 | 光标（自由移动，无限制） | 部件焦点（线性遍历，受布局约束） |
| 功能承载 | 可承载复杂交互和密集信息 | 需简化操作路径，降低信息密度 |

### 1.2 三种适配策略

在设计启动阶段，就需要根据功能的复杂度，选择对应的适配策略，而不是在开发后期再考虑”怎么搬到主机上”。

| 策略 | 特征 | 适用场景 |
|------|------|----------|
| **完全一致** | 双端功能与布局完全相同 | 简单功能，如弹窗确认、单列表选择 |
| **基本一致** | 功能统一，布局基本一致，但对手柄走焦和键位进行专门优化 | 大多数主流功能场景 |
| **重构** | 根据平台交互特性重新设计界面结构和操作流程 | 双端操作差异过大的场景，如背包整理、大地图拖拽等 |

### 1.3 适配策略选择的关键原则

策略选择不是开发阶段的事，而是在需求阶段就必须介入。核心原则有三条：

1. **需求阶段就考虑主机适配性**——一个PC上好用的交互方案，到主机端可能是灾难。不要等界面做完了再去“修修补补”。
2. **发现阻塞性交互问题，立即向策划反馈**——一个操作在主机端需要按五次键才能完成，这在PC端可能只是点两下鼠标。这种差距必须由策划和交互共同在早期解决。
3. **不要侥幸“移植时再说”**——重构成本远高于前期规避。一个布局调整在交互稿阶段改动成本极低，到开发实现后再改，成本呈指数级增长。

## 二、PC端设计要点

PC端的设计是双端适配的起点。好的PC端设计会天然为主机移植预留空间，减少后续的重构成本。

### 2.1 界面布局规范

#### 系统层级原则

- 优先采用“层层深入”的层级结构，每一层聚焦一个明确的任务
- 单个界面内避免嵌套多层子级（下拉菜单嵌套下拉菜单），这会直接导致主机端的走焦困局
- 全界面层级建议不超过4层，超过4层需要重新审视信息架构

#### 通用框架

```
┌─────────────────────────┐
│     顶部导航栏           │  ← 左对齐或居中，提供一级功能入口
├─────────────────────────┤
│                         │
│      中部内容区          │  ← 核心交互区域，承载列表、网格等主要内容
│                         │
├─────────────────────────┤
│     底部键位提示         │  ← PC端为快捷键提示，主机端为手柄键位映射
└─────────────────────────┘
```

### 2.2 排版设计原则

PC端的排版决策，直接影响主机端走焦的体验。

#### 线性排列优先

| 布局类型 | 主机友好度 | 说明 |
|----------|------------|------|
| 线性排列（列表、单行网格） | ★★★★★ | 焦点只需要上下或左右移动，轨迹清晰 |
| 区域分离（左右分栏、四角分布） | ★★☆☆☆ | 焦点需要在不同区域间跳跃，需要额外的跨区切换设计 |

线性排列是主机端最友好的布局方式。如果一个界面在PC端被设计为四角分散的功能按钮，在主机端就需要玩家反复推动摇杆在屏幕对角线上来回移动，操作成本和疲劳感都会显著增加。

#### 部件靠近原则

强关联的控件在物理距离上应该靠近，形成一个操作区。这不仅提高PC端的操作效率，也减少主机端焦点移动的路径长度。

```
反例：物品列表（屏幕左侧） ←→ 制造/使用按钮（屏幕右下角）
问题：主机端玩家需要将焦点从最左侧移动到最右下，路径过长

正例：制造/使用按钮紧邻物品列表，共同构成一个集中的操作区
```

#### 避免悬停展开的父子级

PC端常见的下拉菜单——鼠标悬停父级即自动展开子级——在主机端是行不通的。

```
PC端模式：鼠标悬停父级 → 自动展开子级菜单
问题：主机端没有“悬停”概念，焦点移到父级上就自动展开，会导致移动效率极低

解决方案：选中 ≠ 展开。将“选中父级”和“展开子级”分离为两个操作：
- 焦点移到父级：只选中，不展开
- 按下确认键（○键）：展开子级，进入下一级走焦
```

### 2.3 部件状态设计

每个可交互部件在双端都需要明确定义其各种状态下的视觉表现。常见遗漏是嵌套部件的选中态——比如一个列表项被右键点击时，它既需要“被选中”的视觉反馈，又需要弹出菜单的悬浮关系。

| 状态 | 触发条件 | 常见遗漏场景 |
|------|----------|-------------|
| 常态 | 默认显示 | - |
| 悬浮态（Hover） | 鼠标悬停（PC端特有） | 嵌套在列表中的子部件 |
| 按下态 | 鼠标按下/手柄按键按下 | - |
| 选中态 | 右键菜单/长按/上下文中选中 | 右键菜单场景、多选场景 |
| 禁用态 | 条件不满足，不可操作 | 需明确禁用的视觉样式和走焦行为 |

### 2.4 快捷键设计

#### 操作连贯性原则

| 原则 | 说明 | 反例 |
|------|------|------|
| 设备一致性 | 一组连续操作尽量在同一设备上完成，避免键鼠频繁切换 | 按Esc打开系统菜单，但菜单内只能用鼠标操作，键盘无法选择 |
| 认知负担 | 快捷键的记忆成本不能过高，常用功能优先分配容易记住的键位 | 将高频功能绑定在不常用的冷门键位上 |
| 操作效率 | 减少操作步骤，高频行为提供快捷键 | 每次打开背包都需要三个步骤才能定位到刚获得的物品 |

### 2.5 适配规则

界面需要定义在不同分辨率下的行为，这同样影响主机端在大屏幕电视上的表现。

#### 基础框架适配

```
导航栏 + 操作栏：横向自适应，贴边适配
内容区：左右边距恒定，内容随屏幕尺寸等比变化
```

#### 部件适配规则

| 适配方式 | 适用场景 |
|----------|----------|
| 贴边适配（固定宽度） | 左对齐/右对齐的侧边栏、左右分栏布局 |
| 贴边适配（自适应宽度） | 通屏列表、全宽内容区域 |
| 居中适配（固定宽度） | 居中模态弹窗、小型面板 |
| 居中适配（自适应宽度） | 内容居中展示，背景自适应拉伸 |

## 三、主机端移植要点

这是跨平台UX设计的核心难点。以下所有规范的目标，是让手柄操作达到“不假思索”的直觉级体验。

### 3.1 走焦规则设计

走焦规则是整个主机交互的骨架。规则不清晰，开发实现的走焦行为就会不稳定，玩家的体验就是“焦点乱跳”。

#### 焦点状态模型：同步与异步

这是父子级结构的根本走焦逻辑。

| 关系类型 | 场景 | 行为 |
|----------|------|------|
| **同步** | 父子级在同一界面内 | 焦点移到父级即自动选中，子级内容实时切换展示（不进入新的走焦层级） |
| **异步** | 父子级在不同界面或需要跳转 | 焦点移到父级时不自动执行，需按确认键（○键）跳转进入子级 |

**选择标准**：子级内容不包含可交互元素时用同步，包含可交互元素时用异步。

#### 焦点移动规则

| 规则 | 说明 |
|------|------|
| 移动单位 | 推动一次摇杆/十字键，焦点移动一格 |
| 加速 | 长按十字键或摇杆方向，焦点连续移动并加速 |
| 移动范围 | 限制在当前功能区域内可交互的部件之间 |
| 初始位置 | 每个界面打开时的默认焦点位置，**必须在交互设计文档中明确标注** |

初始位置的遗漏是最常见的走焦设计问题。界面打开后焦点落在哪里，决定了玩家进行下一步操作的起点。通常优先级是：层级最高的界面优先 → 内容区域上到下、左到右 → 核心操作按钮优先。

#### 特殊情况处理

| 场景 | 规则 |
|------|------|
| 末尾循环 | 焦点移动到列表末项后继续向下，是停留在末尾还是循环回首项？需明确定义 |
| 未填满末行 | 网格布局中最后一行不满时，焦点移动到末行最后一个有效部件后如何处理 |

#### 父子级切换模式

| 模式 | 进入子级 | 返回父级 |
|------|----------|----------|
| 模式一：确认/取消 | ○键进入 | ×键返回 |
| 模式二：方向键进出 | 十字键→或L3推入 | 在最左侧继续←或L3推出 |

**注意**：模式二需要在最左侧施加操作缓冲——即在子级最左侧的部件上再按←，不立即触发返回，而是短暂延迟后再推回父级。缺少缓冲会导致玩家在子级内正常浏览时，不小心就触发了返回。

#### 区域间切换

当界面被划分为多个独立的交互区域时（如左右分栏），需要定义区域间的切换规则。

```
边缘跨区：当焦点在区域A的最边缘，继续向区域B的方向推动摇杆时，焦点跳入区域B的默认位置（通常为该区域第一格）
快速切换：通过专用按键（如R3）在几个区域间快速跳转，焦点默认落在目标区域的第一格
```

### 3.2 键位适配规范

#### 键位功能映射

以下映射基于PS5手柄布局，是基于大量主机游戏形成的用户习惯，尽量遵循而不是挑战这些习惯。

| 按键 | 功能 | 说明 |
|------|------|------|
| **○键** | 确定/进入/确认 | 全球多数区域固定为确认；日区可自定义，但强烈建议保持一致 |
| **×键** | 返回/取消/关闭弹窗 | 与○键形成配对记忆 |
| **▲键** | 检视/详情/排序 | 次要功能补充键，通常用于查看物品详情、切换排序方式等 |
| **■键** | 补充功能 | 无特定语义约束，根据功能需要分配 |
| **十字键/L3** | 移动焦点 | 长按加速移动 |
| **R3** | 浏览/翻页/区域切换 | 上/下浏览、左/右切换区域或页面 |
| **L1/R1** | 一级Tab切换 | 可循环，通常用于顶层分类切换 |
| **L2/R2** | 二级Tab切换 | 可循环，通常用于子分类切换 |
| **触摸板** | 打开地图/全屏操作 | PS5触摸板支持滑动和按压两种交互，可承载额外功能 |
| **OPTIONS** | 打开设置菜单 | 约定俗成，几乎所有主机游戏都遵循 |
| **Create键** | 截图/分享 | PS5系统级功能，游戏通常不做映射 |

#### 长按的使用场景

长按是主机端特有的交互手段，用来承载需要二次确认或防止误触的功能。

| 场景 | 目的 |
|------|------|
| 二次确认 | 替代PC端的确认弹窗，长按按钮直接完成确认操作，减少弹窗跳转 |
| 重要功能 | 防止误操作，如删除物品、丢弃装备 |
| 支付行为 | 充值、购买确认，强制玩家有意识地完成操作 |
| 功能补充 | 短按已被占用时，长按承载额外功能。**慎用**，因为长按的可发现性远低于短按 |

#### 键位摆放规则

```
通用交互部件（如关闭按钮）：键位提示靠近操作区，方便玩家一眼看到
主要功能按钮：键位图标直接叠加在按钮上，不需要玩家低头看底部提示
次要功能：统一显示在界面底部的"按键提示区"
PC端的快捷键提示：在主机端直接替换为对应的手柄键位图标，不要保留键盘快捷键提示
```

### 3.3 TRC规则（索尼平台技术规范中与UX设计相关的部分）

这些是索尼对PS5上架游戏提出的技术要求，其中部分直接约束UX设计。

| 规则 | 要求 | 设计影响 |
|------|------|----------|
| **安全区** | 所有重要内容（文字、按钮、HUD）必须显示在画面90%×90%的安全区域内 | 界面边缘必须预留空白，不能把关键UI贴在屏幕最边缘 |
| **加载** | 超过30秒的加载需展示动画，超过60秒需展示进度条 | 需要设计Loading界面，且动画不能是静态图；PS5 SSD性能下加载通常极快，但需考虑跨代兼容场景 |
| **用户名** | 必须能完整显示16字符的Online ID | 玩家名展示区域需要预留足够的字符空间，不能截断 |
| **队伍邀请** | 必须使用系统级邀请功能，操作步骤不超过1次跳转 | 不能使用自定义的第三方邀请弹窗 |
| **关闭游戏** | 必须使用系统标准的关闭方法 | 不能在游戏内添加“退出到桌面”按钮绕过系统关闭流程 |
| **DualSense特性** | 自适应扳机和触觉反馈需有意义的应用 | 不是硬性要求，但善用可显著提升体验评分 |

## 四、焦点设计深度解析

焦点设计是主机端UX最核心、也是最容易被忽略的设计环节。PC端设计师习惯光标思维，而焦点设计需要一套完全不同的思维模型。

### 4.1 焦点基础概念

| 概念 | 定义 |
|------|------|
| **焦点** | 玩家操作的起点，指向当前界面中正在被“指向”的操作对象 |
| **走焦** | 玩家通过摇杆或十字键控制焦点移动的操作过程 |
| **获焦** | 一个控件从无焦点状态变为有焦点状态 |
| **失焦** | 一个控件从有焦点状态变为无焦点状态 |
| **焦点组** | 按功能分区归类的走焦单元，同一组内的焦点按同一套规则移动 |
| **跨焦点组** | 焦点从组A进入组B，触发的边界行为和默认落点逻辑 |

### 4.2 焦点设计三原则

#### 原则一：提供初始

每个界面打开时，必须有一个明确的默认焦点位置。判定优先级为：

```
层级优先：最高层级的界面优先获得焦点
内容优先：同一层级内，遵循上→下、左→右的顺序
核心操作优先：内容区域中，最常使用的功能按钮优先于边缘功能
```

没有初始焦点的界面，玩家打开后不知道焦点在哪里，需要推动摇杆来“找”焦点，这是对体验的严重破坏。

#### 原则二：可遍历

界面上所有可交互元素，都必须能通过方向输入被焦点到达。不能出现某个按钮在PC端可以点击，但在主机端焦点永远走不到的情况。如果某个功能必须存在但极不常用，可以通过快捷键映射来提高到达效率，但不能从走焦路径中移除。

#### 原则三：焦点唯一

同一界面内同一时刻，有且仅有一个焦点。当焦点从一个控件移动到另一个控件时，原控件必须立即失焦，不能出现两个控件同时处于获焦状态的情况。

### 4.3 焦点样式设计

焦点样式是玩家在主机端“看到自己在哪里”的唯一手段，辨识度是最高优先级。

| 要求 | 实现方式 |
|------|----------|
| 辨识度高 | 放大控件、高亮边框、底板颜色变化、循环动效（呼吸光效等） |
| 形态自适应 | 焦点框能根据被选中的控件尺寸和形状自动调整 |
| 视觉统一 | 全游戏使用统一的焦点视觉语言——固定主题色、统一的边框样式、一致的光效 |

### 4.4 走焦顺序规则

#### 就近原则

当玩家向某个方向推动摇杆时，焦点应移动到该方向上距离最近的可交互控件。设计时需要考虑X轴和Y轴的权重分配——横向移动时降低Y轴权重，纵向移动时降低X轴权重，避免焦点“偏航”。

#### 十字运动原则

焦点移动的方向必须与玩家推动摇杆的方向一致。左摇杆和十字键的走焦行为必须完全相同，两个操作方式共用同一套走焦逻辑。

#### 焦点记忆路径

当玩家从父级进入子级再返回父级时，焦点应该回到哪里？

```
无记忆：从子级返回父级时，焦点回到父级区域的默认位置（通常是第一行第一个）
有记忆：返回时焦点回到进入子级前在父级中的位置
```

记忆路径适用于：侧边多层结构、固定区域的屏外延伸列表。不记忆路径适用于：临时弹窗关闭后返回主界面。

### 4.5 常见走焦场景速查表

| 场景 | 焦点运动方式 |
|------|-------------|
| 同行/同列移动 | 在当前行/列上判断方向上最近的控件 |
| 跨行移动 | 从当前行首/尾触发移动时，自动跳转到下一行/上一行的行首/行尾 |
| 非整列节点 | 网格中控件大小不一或布局不规则时，使用就近原则 |
| 屏外延伸（滚动列表） | 焦点固定在列表中某一位置，内容向上/向下滚动 |
| 同屏多层（侧边栏+详情区） | 焦点记忆路径，返回时回到离开前的位置 |
| 跨页/跨层级 | 优先使用焦点记忆，无记忆时回到默认位置 |
| 文本输入 | 方向键控制插入符在字符间移动 |

## 五、光标与焦点的选择

### 5.1 核心差异

| 维度 | 光标模式 | 焦点模式 |
|------|----------|----------|
| 移动方式 | 摇杆控制光标位置（模拟鼠标） | 摇杆方向 = 焦点移动方向 |
| 界面布局限制 | 无限制，可以到达屏幕任意位置 | 受布局约束，必须线性可遍历 |
| 移动自由度 | 高，可以斜向移动、任意位置停止 | 低，只能按设计好的路径移动 |
| 主机适配度 | 差——光标模拟鼠标精度不足、速度慢、操作疲劳 | 好——符合手柄输入特性，操作效率高 |

### 5.2 混合模式

近年的主机游戏越来越多采用“光标 + 焦点”的混合模式，典型应用场景如地图界面、背包整理等需要大量自由选择的操作。PS5的触摸板也为光标操作提供了额外的可能性。

```
触发规则（当玩家同时使用光标和焦点时）：
├── 光标瞬移到当前焦点位置 [推荐]—— 两者始终同步，体验最流畅
├── 光标保持原位—— 可能导致两个标识同时存在，造成混淆
└── 光标置于画面中心—— 适用于大地图等全屏浏览场景
```

### 5.3 模式选择

```
基于PC端开发的项目 → 采用“光标为主 + 焦点辅助”或纯光标模式
基于主机端开发的项目 → 采用纯焦点模式
```

纯焦点模式的主机体验优于混合模式，因为玩家不需要在“移动光标”和“移动焦点”两种心智模型之间切换。但纯焦点模式要求界面布局高度线性化，对PC端的视觉设计提出了更高的约束。

## 六、设计决策框架

以下框架展示了从项目启动到最终实现的双端UX设计决策路径：

```
项目启动
    │
    ├─→ 明确双端关系：PC为主开发？主机为主开发？同步开发？
    │
    ├─→ 选择适配策略
    │       ├─→ 功能简单 → 完全一致（双端同一套UI）
    │       ├─→ 主流功能 → 基本一致（共用UI，主机优化走焦和键位）
    │       └─→ 差异过大 → 重构（双端独立设计UI）
    │
    ├─→ PC端设计阶段
    │       ├─→ 布局采用线性排列优先
    │       ├─→ 关联控件靠拢，悬停展开改为选中+确认展开
    │       └─→ 快捷键与主机键位提前映射
    │
    ├─→ 主机移植阶段
    │       ├─→ 设计走焦规则：初始焦点、遍历路径、跨区切换
    │       ├─→ 键位映射：遵循约定俗成，保持一致性
    │       └─→ TRC合规：安全区、加载、用户名等
    │
    └─→ 验证阶段
            ├─→ 手柄完整走一遍所有界面，记录焦点异常和路径过长
            └─→ 大屏幕电视实机验证安全区和文字可读性
```

## 总结

跨平台移植的UX工作，核心是在PC端的“光标自由”和主机端的“焦点约束”之间找到平衡点。这不是一个在开发后期用技术手段能“修”好的问题，而是一个必须在设计前期就贯彻到每一个布局决策中的设计思维。

| 设计维度 | 核心问题 | 解决方案 |
|----------|----------|----------|
| **双端策略** | 功能复杂度与主机操作能力的冲突 | 以“基本一致”为主策略，必要时不回避重构 |
| **PC布局** | PC设计如何不成为主机移植的障碍 | 线性排列优先，关联控件集中，悬停展开改为确认展开 |
| **主机走焦** | 焦点从哪里开始、怎么走、走到哪 | 初始焦点+就近原则+十字运动+记忆路径四根支柱 |
| **键位适配** | 手柄有限按键如何承载PC端的复杂操作 | 遵循约定俗成的基础映射，通过组合键和长按扩展能力 |
| **TRC合规** | 平台技术规范对设计的硬约束 | 安全区、加载动画、用户名字符空间，从设计稿阶段就嵌入考虑 |

最终目标不是让主机端“能用”，而是让主机玩家拿起手柄时，感受到的是为手柄而生的一气呵成，而不是“用鼠标设计的界面硬塞给了手柄”的违和感。
